     1→# Project Engineering Skills & Standards
     2→
     3→## Purpose
     4→
     5→Use this file as the default engineering standard for all new web, SaaS, API, AI-agent, automation, dashboard, and e-commerce projects. The goal is to build software that is **fast, secure, maintainable, scalable, accessible, SEO-friendly, observable, and production-ready** from the beginning.
     6→
     7→---
     8→
     9→# 1. Core Engineering Principles
    10→
    11→- Prefer simple, boring, maintainable architecture over unnecessary complexity.
    12→- Design for production from the first implementation, not as a later cleanup task.
    13→- Reuse existing libraries and project utilities before creating custom replacements.
    14→- Keep business logic independent from UI, framework, database, and external providers where practical.
    15→- Use clear naming, small modules, typed interfaces, validation, and predictable error handling.
    16→- Never hard-code secrets, credentials, API keys, tokens, or environment-specific configuration.
    17→- Make important operations idempotent where possible.
    18→- Design APIs and database schemas around real use cases and expected growth.
    19→- Measure performance instead of guessing.
    20→- Automate repetitive checks with linting, formatting, tests, CI, and security scanning.
    21→
    22→---
    23→
    24→# 2. Project Discovery Before Coding
    25→
    26→Before implementation:
    27→
    28→1. Inspect the existing repository structure.
    29→2. Identify the framework, runtime, package manager, database, deployment target, and existing conventions.
    30→3. Read existing documentation and configuration files.
    31→4. Identify reusable components and utilities.
    32→5. Inspect database schema and migrations before changing data models.
    33→6. Identify authentication, authorization, integrations, queues, cron jobs, storage, and external APIs.
    34→7. Define functional requirements and non-functional requirements.
    35→8. Define expected traffic, data volume, concurrency, latency targets, and availability requirements.
    36→9. Identify deployment limitations such as shared hosting, cPanel, serverless, containers, or VPS.
    37→10. Produce an implementation plan before making large architectural changes.
    38→
    39→Do not rewrite working systems merely for stylistic reasons.
    40→
    41→---
    42→
    43→# 3. System Design
    44→
    45→Every significant project should have a lightweight system design covering:
    46→
    47→- Users and roles
    48→- Main business workflows
    49→- Frontend architecture
    50→- Backend/API architecture
    51→- Database architecture
    52→- Authentication and authorization
    53→- File/object storage
    54→- Caching
    55→- Background jobs and queues
    56→- External integrations
    57→- Observability
    58→- Security boundaries
    59→- Deployment architecture
    60→- Backup and disaster recovery
    61→- Scaling strategy
    62→- Failure modes
    63→
    64→## Recommended logical architecture
    65→
    66→```text
    67→Browser / Mobile / Client
    68→        |
    69→        v
    70→CDN / Edge / WAF
    71→        |
    72→        v
    73→Frontend / BFF / API Gateway
    74→        |
    75→   +----+----------------+
    76→   |                     |
    77→   v                     v
    78→Application API      Background Jobs
    79→   |                     |
    80→   +----------+----------+
    81→              |
    82→       Service / Domain Layer
    83→              |
    84→     +--------+---------+
    85→     |        |         |
    86→     v        v         v
    87→ Database   Cache    Object Storage
    88→     |
    89→     v
    90→Backups / Replicas
    91→```
    92→
    93→For small projects, keep this logical separation without creating unnecessary microservices.
    94→
    95→## Monolith vs services
    96→
    97→Prefer a modular monolith until independent deployment, scaling, ownership, or reliability requirements justify service separation.
    98→
    99→Use microservices only when there is a clear operational reason such as:
   100→
   101→- independently scaling workloads
   102→- independently deploying high-risk components
   103→- strict isolation requirements
   104→- separate team ownership
   105→- different runtime requirements
   106→- asynchronous/event-driven workloads at meaningful scale

   109→
   110→# 4. Fast Website / Performance Engineering
   111→
   112→Performance is a first-class feature.
   113→
   114→## Target principles
   115→
   116→Aim for:
   117→
   118→- Fast first response
   119→- Minimal JavaScript
   120→- Minimal CSS
   121→- Small HTML payloads
   122→- Optimized images
   123→- Efficient database queries
   124→- Aggressive but safe caching
   125→- CDN/edge delivery where useful
   126→- Streaming or progressive rendering for expensive content
   127→- No unnecessary client-side work
   128→
   129→## Loading strategy
   130→
   131→### Critical rendering path
   132→
   133→1. Return useful HTML quickly.
   134→2. Inline only genuinely critical CSS when justified.
   135→3. Defer non-critical JavaScript.
   136→4. Preload only high-priority resources.
   137→5. Avoid render-blocking third-party scripts.
   138→6. Lazy-load below-the-fold media.
   139→7. Reserve image dimensions to prevent layout shift.
   140→8. Use modern image formats such as AVIF/WebP where supported.
   141→9. Compress text assets with Brotli or gzip.
   142→10. Use long-lived immutable caching for fingerprinted static assets.
   143→
   144→### JavaScript
   145→
   146→- Prefer server rendering or static rendering for content-heavy pages.
   147→- Ship only the JavaScript required for the current page.
   148→- Split large bundles.
   149→- Lazy-load expensive components.
   150→- Remove unused dependencies.
   151→- Avoid large client-side state stores unless needed.
   152→- Avoid hydration of components that do not need interactivity.
   153→- Use Web Workers for appropriate CPU-heavy browser tasks.
   154→
   155→### Images
   156→
   157→- Resize images to their actual display size.
   158→- Generate responsive variants with `srcset`/`sizes`.
   159→- Use `loading="lazy"` for non-critical images.
   160→- Do not lazy-load the primary above-the-fold hero image when it is the LCP element.
   161→- Use `fetchpriority="high"` selectively for the primary LCP resource.
   162→- Strip unnecessary metadata.
   163→- Generate thumbnails rather than downloading full-size images everywhere.
   164→
   165→### Fonts
   166→
   167→- Use a limited number of font families and weights.
   168→- Prefer self-hosted fonts when appropriate.
   169→- Preload only critical fonts.
   170→- Use `font-display: swap` or an appropriate fallback strategy.
   171→- Avoid loading dozens of unused font weights.
   172→

   175→# 5. Core Web Vitals
   176→
   177→Track and optimize:
   178→
   179→- **LCP** — Largest Contentful Paint
   180→- **INP** — Interaction to Next Paint
   181→- **CLS** — Cumulative Layout Shift
   182→
   183→Also monitor:
   184→
   185→- TTFB
   186→- FCP
   187→- total transfer size
   188→- JavaScript execution time
   189→- long tasks
   190→- API latency
   191→- database latency
   192→
   193→Performance work should be validated with real measurements in addition to local development testing.
   194→
   195→---
   196→
   197→# 6. Backend Performance
   198→
   199→- Avoid N+1 database queries.
   200→- Select only required columns.
   201→- Add indexes based on actual query patterns.
   202→- Paginate large collections.
   203→- Use cursor pagination for very large datasets where appropriate.
   204→- Cache expensive and stable reads.
   205→- Batch writes when appropriate.
   206→- Use connection pooling.
   207→- Move long-running operations to background jobs.
   208→- Stream large files instead of loading them fully into memory.
   209→- Apply request timeouts to external services.
   210→- Use retries with exponential backoff only for retryable failures.
   211→- Prevent retry storms.
   212→- Use circuit breakers where external dependency failures can cascade.
   213→
   214→---
   215→
   216→# 7. Database Design
   217→
   218→- Use migrations for schema changes.
   219→- Use foreign keys and constraints where appropriate.
   220→- Add indexes for real query patterns.
   221→- Avoid indexing every column.
   222→- Use transactions for multi-step consistency requirements.
   223→- Keep large blobs out of relational tables when object storage is more appropriate.
   224→- Add audit fields such as `created_at` and `updated_at` where useful.
   225→- Use soft deletion only when there is a concrete business requirement.
   226→- Plan retention and archival for high-volume tables.
   227→- Back up production databases automatically.
   228→- Test restoration, not only backup creation.
   229→
   230→---
   231→
   232→# 8. Caching Strategy
   233→
   234→Use cache layers deliberately:
   235→
   236→```text
   237→Browser Cache
   238→     -> CDN / Edge Cache
   239→     -> Application Cache
   240→     -> Database
   241→```
   242→
   243→Possible technologies include browser HTTP caching, CDN caching, Redis, in-process caches, and database query/result caching.
   244→
   245→Rules:
   246→
   247→- Define cache keys clearly.
   248→- Define TTLs.
   249→- Define invalidation rules.
   250→- Avoid caching private user data in shared caches.
   251→- Prevent cache stampedes.
   252→- Never rely on cache as the only source of durable data.
   253→
   254→---
   255→
   256→# 9. API Design
   257→
   258→- Version public APIs when compatibility requires it.
   259→- Use consistent resource naming.
   260→- Validate all input at the boundary.
   261→- Return predictable error structures.
   262→- Use appropriate HTTP status codes.
   263→- Support pagination, filtering, sorting, and search intentionally.
   264→- Apply authentication and authorization to every protected operation.
   265→- Add rate limits to abuse-prone endpoints.
   266→- Use idempotency keys for operations where duplicate requests can cause damage.
   267→- Document APIs with OpenAPI where appropriate.
   268→- Never expose internal stack traces or secrets to clients.
   269→
   270→---
   271→
   272→# 10. Security
   273→
   274→Security must be designed into the system rather than added after deployment.
   275→
   276→## Application security
   277→
   278→- Validate and sanitize untrusted input.
   279→- Use parameterized queries/ORM protections against SQL injection.
   280→- Protect against XSS.
   281→- Protect state-changing requests against CSRF where applicable.
   282→- Prevent SSRF in URL-fetching features.
   283→- Validate file uploads by type, size, extension, content, and storage location.
   284→- Prevent path traversal.
   285→- Use secure session handling.
   286→- Apply least privilege.
   287→- Enforce authorization server-side; never trust UI restrictions.
   288→- Avoid exposing sensitive information in logs.
   289→- Add security headers where appropriate.
   290→- Configure CORS narrowly.
   291→- Use HTTPS in production.
   292→- Keep dependencies patched.
   293→
   294→## Authentication
   295→
   296→- Store passwords using strong password hashing such as Argon2id or an appropriate modern equivalent.
   297→- Never store plaintext passwords.
   298→- Support secure session expiration and revocation.
   299→- Protect login and password-reset endpoints against abuse.
   300→- Use MFA for sensitive applications where appropriate.
   301→- Rotate compromised credentials immediately.
   302→
   303→## Secrets
   304→
   305→Never commit:
   306→
   307→- API keys
   308→- database passwords
   309→- private keys
   310→- OAuth client secrets
   311→- JWT signing secrets
   312→- cloud credentials
   313→
   314→Use environment variables or a proper secret manager.
   315→
   316→## Security headers
   317→
   318→Consider:
   319→
   320→- Content-Security-Policy
   321→- Strict-Transport-Security
   322→- X-Content-Type-Options
   323→- Referrer-Policy
   324→- Permissions-Policy
   325→- frame-ancestors / appropriate clickjacking protection
   326→
   327→Do not blindly copy a header configuration; test it against application requirements.
   328→

   330→
   331→# 11. SEO
   332→
   333→For public websites, implement technical SEO from the beginning.
   334→
   335→- Semantic HTML.
   336→- Correct title and meta description.
   337→- Canonical URLs.
   338→- XML sitemap.
   339→- robots.txt.
   340→- Open Graph metadata.
   341→- Twitter/X card metadata where useful.
   342→- Structured data/schema where applicable.
   343→- Clean URL architecture.
   344→- Proper heading hierarchy.
   345→- Internal linking.
   346→- 404 and redirect handling.
   347→- Pagination/canonical strategy for large collections.
   348→- Fast mobile rendering.
   349→- Accessible navigation.
   350→- Avoid indexing duplicate, private, filtered, or low-value URLs unintentionally.
   351→
   352→For dynamic sites, generate metadata from authoritative content rather than duplicating it manually.
   353→
   354→---
   355→
   356→# 12. Accessibility
   357→
   358→Target WCAG-aligned accessible interfaces.
   359→
   360→- Use semantic HTML first.
   361→- Keyboard navigation must work.
   362→- Provide visible focus states.
   363→- Use labels for form controls.
   364→- Provide useful alt text for meaningful images.
   365→- Mark decorative images appropriately.
   366→- Maintain adequate color contrast.
   367→- Do not rely on color alone to communicate state.
   368→- Use ARIA only when native HTML is insufficient.
   369→- Support screen readers for important workflows.
   370→- Respect reduced-motion preferences.
   371→
   372→---
   373→
   374→# 13. Frontend Architecture
   375→
   376→- Use reusable components.
   377→- Keep components focused.
   378→- Separate presentation from business logic where practical.
   379→- Keep forms validated on both client and server.
   380→- Handle loading, empty, success, error, and permission states.
   381→- Use optimistic UI only where rollback is well-defined.
   382→- Avoid unnecessary global state.
   383→- Preserve URL state for useful filters/search where appropriate.
   384→- Design responsive layouts from mobile to desktop.
   385→- Avoid layout shifts caused by asynchronous content.
   386→
   387→For Next.js or similar frameworks:
   388→
   389→- Prefer server components/rendering for non-interactive content.
   390→- Keep client components small.
   391→- Use route-level code splitting.
   392→- Cache stable server data appropriately.
   393→- Avoid accidentally converting large parts of the application into client components.
   394→
   395→---
   396→
   397→# 14. UX Standards
   398→
   399→Every important page should handle:
   400→
   401→- loading state
   402→- empty state
   403→- error state
   404→- success feedback
   405→- permission denied state
   406→- offline/network failure where applicable
   407→- destructive action confirmation
   408→
   409→Interfaces should be responsive, keyboard-friendly, and consistent.
   410→
   411→Avoid unnecessary animations, popups, spinners, and blocking dialogs.
   412→
   413→---
   414→
   415→# 15. AI / Agent Projects
   416→
   417→For AI systems:
   418→
   419→- Separate model provider configuration from business logic.
   420→- Support provider fallback where reliability requires it.
   421→- Use structured outputs when possible.
   422→- Validate model outputs before executing actions.
   423→- Require approval for high-impact or destructive actions.
   424→- Apply tool-level permissions.
   425→- Log model/tool traces without leaking secrets.
   426→- Bound context size and token usage.
   427→- Cache deterministic or reusable work where appropriate.
   428→- Add timeouts and retries for model APIs.
   429→- Design provider abstraction so models can be replaced.
   430→- Never allow model-generated instructions to bypass authorization.
   431→- Treat retrieved web/file content as untrusted input.
   432→- Add prompt-injection defenses for tool-using agents.
   433→
   434→Recommended agent flow:
   435→
   436→```text
   437→User Request
   438→    -> Intent / Task Analysis
   439→    -> Permission Check
   440→    -> Plan
   441→    -> Tool Selection
   442→    -> Tool Execution
   443→    -> Validation
   444→    -> Optional Human Approval
   445→    -> Result
   446→    -> Audit / Trace
   447→```
   448→

   450→
   451→# 16. Scraping / Crawling Systems
   452→
   453→For crawlers and website audit tools:
   454→
   455→- Respect robots.txt and applicable site policies.
   456→- Implement concurrency limits.
   457→- Use request timeouts.
   458→- Retry only transient failures.
   459→- Rotate proxies only when legitimately required and permitted.
   460→- Deduplicate URLs and content.
   461→- Normalize URLs.
   462→- Detect canonical URLs.
   463→- Store crawl state incrementally.
   464→- Stream or batch large exports.
   465→- Avoid loading browser automation for pages that can be fetched with HTTP.
   466→- Use browser rendering only when required by JavaScript behavior.
   467→- Cache reusable resources.
   468→- Track status codes, redirects, latency, content type, and crawl errors.
   469→- Prevent infinite crawl loops and unbounded URL generation.
   470→
   471→---
   472→
   473→# 17. File Uploads and Storage
   474→
   475→- Store uploads outside executable web roots where possible.
   476→- Generate server-side filenames.
   477→- Limit file size.
   478→- Validate MIME type and actual file content.
   479→- Scan files where risk warrants it.
   480→- Prevent executable uploads.
   481→- Use object storage for large media when appropriate.
   482→- Use signed URLs for private downloads.
   483→- Apply retention and cleanup policies.
   484→

   486→
   487→# 18. Background Jobs
   488→
   489→Use queues for:
   490→
   491→- email sending
   492→- image processing
   493→- video processing
   494→- scraping
   495→- report generation
   496→- AI workloads
   497→- imports/exports
   498→- scheduled maintenance
   499→
   500→Each job should have:
   501→
   502→- unique/job ID
   503→- retry policy
   504→- timeout
   505→- status
   506→- error details
   507→- idempotency strategy
   508→- dead-letter handling where appropriate
   509→- progress reporting for long operations
   510→
   511→---
   512→
   513→# 19. Observability
   514→
   515→Production systems should provide:
   516→
   517→- structured logs
   518→- request IDs / correlation IDs
   519→- metrics
   520→- error tracking
   521→- health checks
   522→- dependency health checks
   523→- performance measurements
   524→- audit logs for sensitive actions
   525→
   526→Track at minimum:
   527→
   528→- request rate
   529→- error rate
   530→- latency
   531→- database latency
   532→- queue depth
   533→- job failures
   534→- cache hit/miss rate where relevant
   535→- resource utilization
   536→
   537→Never log passwords, tokens, private keys, full payment details, or unnecessary personal data.
   538→

   540→
   541→# 20. Reliability and Failure Design
   542→
   543→Design for failure:
   544→
   545→- external APIs can fail
   546→- databases can become unavailable
   547→- queues can back up
   548→- DNS/CDN can fail
   549→- users can submit duplicate requests
   550→- workers can crash midway through a job
   551→- deployments can fail
   552→
   553→Use:
   554→
   555→- timeouts
   556→- retries with backoff
   557→- idempotency
   558→- graceful degradation
   559→- circuit breakers where appropriate
   560→- health checks
   561→- transactional boundaries
   562→- rollback/feature flags for risky releases
   563→- backups and tested restoration procedures
   564→

   566→
   567→# 21. Deployment
   568→
   569→Before production:
   570→
   571→- production environment variables configured
   572→- HTTPS enabled
   573→- database migrations tested
   574→- backups configured
   575→- restore process tested
   576→- error monitoring enabled
   577→- logging configured
   578→- security headers reviewed
   579→- CORS reviewed
   580→- rate limiting reviewed
   581→- cron/queue workers verified
   582→- storage permissions reviewed
   583→- build artifacts verified
   584→- cache behavior tested
   585→- rollback procedure documented
   586→
   587→For restricted shared hosting/cPanel environments, prefer architecture that matches available runtimes. If Node.js is unavailable, do not assume a Next.js server can run there; consider static export, PHP backend, a supported runtime, or external application hosting.

   591→# 22. Testing
   592→
   593→Use multiple testing layers:
   594→
   595→### Unit tests
   596→
   597→Business rules, utility functions, validators, transformations.
   598→
   599→### Integration tests
   600→
   601→Database, APIs, queues, storage, and external-service adapters.
   602→
   603→### End-to-end tests
   604→
   605→Critical user journeys such as authentication, checkout, dashboard workflows, and administration.
   606→
   607→### Performance tests
   608→
   609→Measure representative workloads and concurrency.
   610→
   611→### Security tests
   612→
   613→Check authentication, authorization, injection risks, uploads, SSRF, dependency vulnerabilities, and exposed secrets.
   614→
   615→Do not treat high test coverage as proof of correctness; test important behavior and failure modes.
   616→

   619→# 23. CI/CD Quality Gates
   620→
   621→A production repository should ideally run:
   622→
   623→```text
   624→Install
   625→  -> Type Check
   626→  -> Lint
   627→  -> Format Check
   628→  -> Unit Tests
   629→  -> Integration Tests
   630→  -> Build
   631→  -> Security / Dependency Scan
   632→  -> Deployment
   633→  -> Smoke Test
   634→```
   635→
   636→Block deployment when critical checks fail.

   640→# 24. Code Quality
   641→
   642→Use:
   643→
   644→- TypeScript strict mode where applicable.
   645→- Python type hints where practical.
   646→- ESLint/formatter or equivalent tooling.
   647→- Ruff/Black/MyPy or project-appropriate Python tooling.
   648→- Clear module boundaries.
   649→- Small functions.
   650→- Explicit error handling.
   651→- No dead code.
   652→- No duplicated business logic.
   653→- No unexplained magic constants.
   654→
   655→Comments should explain **why**, not merely repeat what the code does.

   659→# 25. Dependency Management
   660→
   661→Before adding a dependency:
   662→
   663→1. Check whether the framework already provides the feature.
   664→2. Check maintenance activity.
   665→3. Check license compatibility.
   666→4. Check bundle/runtime impact.
   667→5. Check security history.
   668→6. Check whether a smaller dependency solves the problem.
   669→
   670→Keep dependencies updated, but test upgrades before production deployment.

   718→# 28. Project Structure
   719→
   720→Use a structure appropriate to the framework, but keep responsibilities clear.
   721→
   722→Example:
   723→
   724→```text
   725→project/
   726→├── app/ or src/
   727→│   ├── components/
   728→│   ├── pages/ or routes/
   729→│   ├── features/
   730→│   ├── services/
   731→│   ├── domain/
   732→│   ├── repositories/
   733→│   ├── validators/
   734→│   ├── lib/
   735→│   └── config/
   736→├── tests/
   737→├── scripts/
   738→├── migrations/
   739→├── public/
   740→├── docs/
   741→├── .env.example
   742→├── README.md
   743→├── ARCHITECTURE.md
   744→└── SECURITY.md
   745→```
   746→
   747→Do not force this exact structure onto every framework; use the same separation of concerns with framework-native conventions.

   787→# 30. Default Definition of Done
   788→
   789→A feature is not complete when the code merely works locally.
   790→
   791→A feature is complete when:
   792→
   793→1. The intended behavior works.
   794→2. Invalid input is handled safely.
   795→3. Permissions are enforced server-side.
   796→4. Loading, empty, success, and failure states are handled.
   797→5. Data integrity is preserved.
   798→6. Performance is acceptable for the expected workload.
   799→7. Security implications have been reviewed.
   800→8. Tests cover important behavior.
   801→9. Logs/metrics exist where operationally useful.
   802→10. Documentation is updated.
   803→11. Deployment behavior is verified.
   804→12. The implementation does not introduce unnecessary technical debt.

   948→
   949→Design for real layouts rather than fixed device screenshots.
   950→

   967→

   976→- Cache reusable drawing resources.

   993→# 39. 3D Design and Rendering
   994→
   995→For 3D experiences:
   996→
   997→- Define world, camera, and object coordinate systems.
   998→- Use reusable models and materials.
   999→- Keep polygon counts appropriate for the target device.
  1000→- Compress textures.
  1001→- Use texture atlases where useful.
  1002→- Prefer instancing for repeated objects.
  1003→- Use level-of-detail (LOD) for large scenes.
  1004→- Frustum-cull objects outside the camera view.
  1005→- Avoid unnecessary transparent materials.
  1006→- Reuse geometries and materials.
  1007→- Dispose GPU resources correctly.
  1008→- Keep post-processing effects proportional to device capability.
  1009→
  1010→Recommended conceptual pipeline:
  1011→
  1012→```text
  1013→Input
  1014→  -> Scene State
  1015→  -> Physics / Logic
  1016→  -> Animation
  1017→  -> Camera
  1018→  -> Culling / LOD
  1019→  -> Geometry
  1020→  -> Materials / Textures
  1021→  -> Lighting
  1022→  -> Rendering

  1024→  -> Display

  1045→# 41. Animation and Motion
  1046→
  1047→Animation must communicate state, hierarchy, causality, or spatial relationships.
  1048→
  1049→Use motion for:
  1050→
  1051→- entering/exiting elements
  1052→- state changes
  1053→- feedback
  1054→- navigation transitions
  1055→- loading progress
  1056→- drag/drop
  1057→- expanding/collapsing content
  1058→- visualizing physical movement
  1059→
  1060→Avoid animation that delays the user or creates visual noise.
  1061→
  1062→Rules:
  1063→
  1064→- Keep transitions short for ordinary UI feedback.
  1065→- Use consistent easing.
  1066→- Animate transforms and opacity where possible.
  1067→- Avoid animating expensive layout properties unnecessarily.
  1068→- Respect `prefers-reduced-motion`.
  1069→- Do not block interaction while decorative animation is running.
  1070→- Provide deterministic animation state when testing.

  1089→

  1138→
  1139→When implementing physics, distinguish simulation time from rendering time.
  1140→
  1141→Typical concepts:
  1142→
  1143→- position
  1144→- velocity
  1145→- acceleration
  1146→- mass
  1147→- force
  1148→- impulse
  1149→- friction
  1150→- restitution
  1151→- gravity
  1152→- drag
  1153→- angular velocity
  1154→- torque
  1155→- collision detection
  1156→- collision response
  1157→
  1158→Basic integration concept:
  1159→
  1160→```text
  1161→velocity += acceleration * dt
  1162→position += velocity * dt
  1163→```

  1165→Use a stable timestep for simulations that require deterministic or predictable behavior.
  1166→
  1167→Do not use frame rate directly as a substitute for elapsed time.

  1172→
  1173→Choose collision algorithms based on object complexity.
  1174→

  1176→
  1177→- point vs rectangle
  1178→- circle vs circle
  1179→- circle vs rectangle
  1180→- AABB
  1181→- OBB
